# adr-sandboxed-scripting — sandboxed Lua scripting

- **Status:** accepted, implemented (round two — see below; originally landed decision-only)
- **Date:** 2026-07-30
- **Touches SPEC:** §1.2 (Non-Goals), §3.1 (pipeline purity), §6 (`<script>`/`onclick`/window-hint
  `<meta>`), §20 q-sandboxed-scripting, q-websocket-support (note only)

## Context

`adr-extension-server` gives extensions a real path to be plain HTML, served internally and
browsed like any other page. That covers anything whose interactivity is naturally
request/response — a form, a click that reloads a page. It doesn't cover anything that wants to
react *instantly*, client-side, without a round trip: a live counter, a calculator that updates as
you type instead of on submit, or — the concrete motivating case — `EventViewerWindow`
(`adr-native-demo-windows`), which shows tvshow's own live event stream and has no way to become
"externally fetchable content" the way a calculator does, because there's nothing to fetch: the
data is generated by user interaction with tvshow itself, continuously.

The question this ADR answers: what would let *any* server-backed extension get that kind of
live, client-side update, without inventing a bespoke mechanism per feature the way
`adr-extension-ui-protocol`'s widget protocol did? Three shapes were considered (see Alternatives);
the direction chosen is scripting — but scripting is a large, real feature (new dependency, new
pipeline stage, a non-goal reversal), and this session's other two initiatives (native-window
keyboard polish, the extension server skeleton) were already substantial. Rather than rush a
scripting engine alongside both, or skip it and leave the direction undocumented, this ADR records
the decision and its shape now, so `adr-extension-server`'s design doesn't paint itself into a
corner, without committing the implementation to this pass.

## Decision

**Reverse SPEC §1.2's "No JavaScript execution" non-goal into "no arbitrary/untrusted client-side
execution."** The non-goal was never really about JavaScript specifically — it was about running
page-supplied code with no containment, on a codebase whose entire risk posture
(`adr-multiprocess-sandboxing`) already leans on "no user-supplied code executes with the user's
own privileges beyond what an explicit extension install already grants." A *sandboxed* embedded
interpreter doesn't violate that posture; an unsandboxed one would.

**Lua is the leading candidate** for the interpreter, not chosen with finality here but recorded
as the working assumption: small (single-digit-MB, often just a handful of `.c` files), the
single most commonly embedded scripting language in exactly this "host application drives a
tightly sandboxed guest" role, trivial to build without its `io`/`os` standard libraries (the
sandboxing mechanism itself — no filesystem, no process spawn, no network from script code; those
libraries simply wouldn't be linked in), MIT-licensed. Alternatives (Wren, a hand-rolled tiny DSL)
aren't ruled out, but Lua is the default a real implementation pass should start from.

**Shape of the eventual work** (not built now):

- A new **pure** pipeline stage, per SPEC §3.1's existing purity discipline: script execution
  takes a DOM snapshot + an event (click, timer tick, input change) and produces DOM mutations —
  no I/O, no globals, no `TApplication` reference, deterministic given the same inputs. This keeps
  it testable the same way every other pipeline stage is (golden tests, no terminal needed), and
  keeps the sandboxing guarantee structural rather than just "the interpreter happens not to have
  those libraries linked" — a pure stage *can't* reach the filesystem or network even if something
  upstream misconfigured the interpreter build.
- An event-binding model: `on_click`-style handlers, since that's the interaction vocabulary forms
  and links already establish — not a generic DOM-event-listener API surface, at least not in a
  first pass.
- Explicit sandboxing guarantees a real implementation must uphold: no filesystem access, no
  network access, no process spawn, and a bound on unbounded loops (an instruction-count or
  wall-clock budget per script invocation — exact mechanism TBD at implementation time, but "a
  script can hang the render pipeline" is not acceptable given §1.1's pure-render-path mission).

**Not decided here**: exact Lua API surface, how DOM mutations get expressed to script code, how
this interacts with `layout::engine`'s existing pure-function contract, timer/interval semantics.
Those are implementation-time design questions for whenever this actually gets built.

## Round two: implementation

Built the same session, once the user asked for it directly ("go with Lua") rather than staying
decision-only. What actually shipped, against the "not decided here" list above:

- **Dependency**: `lua/lua` (upstream mirror, MIT), pinned `v5.4.7`, vendored the same way
  gumbo/katana are (`cmake/Lua.cmake` — no CMakeLists.txt upstream, glob-compile the sources).
  One real gotcha: the glob also picks up `onelua.c` (Lua's "everything in one translation unit"
  alternative build — `#include`s every other `.c` file as text and defines its own `main()` by
  default) alongside the normal per-file sources; compiling both together double-defines every
  Lua API symbol in the resulting `.a`. `ar` doesn't complain (it doesn't resolve symbols), so
  this doesn't surface until something links against the library — caught by actually linking
  (`cmake --build build --target lua_lib`), not by the `ar` step succeeding. Excluded alongside
  `lua.c`/`ltests.c`.
- **Session lifetime, not per-call**: the ADR's "not decided here" list didn't flag this, but it
  turned out to be the one design point that would have silently broken the calculator if gotten
  wrong: a script's top-level `local` variables (a running total, say) are upvalues closed over by
  its `function` globals, and closures only keep working across calls if the VM that created them
  stays alive. `LuaSession` (`client/include/tvshow/script/lua_engine.hpp`) is therefore one
  `lua_State` per **loaded page**, not per click — created once (running the script's top level,
  defining its functions and initializing its locals), then `call(handler_name)` just invokes an
  already-defined global on the same VM. `BrowserView` owns one `std::optional<LuaSession>`,
  (re)bound in `bind_lua_session()` at every point `page_` gets replaced (initial construction,
  async navigation, and `submit_form()`'s synchronous POST path — three call sites, easy to miss
  one and leave a session dangling against a destroyed `Document`).
- **Sandboxing, as designed**: only `base`/`string`/`math`/`table` opened via `luaL_requiref`
  (never `luaL_openlibs`, which would also pull in `io`/`os`/`package`/`debug`); `load`/
  `loadstring`/`dofile`/`loadfile`/`require` explicitly nilled out of `base` after opening it; an
  instruction-count hook (`lua_sethook(..., LUA_MASKCOUNT, 200000)`, reset per `call()`) aborts a
  runaway loop deterministically. All four claims are regression-tested, not just asserted in
  comments — `tests/unit/script/lua_engine_test.cpp` checks `io`/`os`/`load`/`require` are `nil`
  from inside a script, and that `while true do end` actually gets bounded rather than hanging the
  test suite.
- **Mutation API**: `tv.set_text(id, str)` / `tv.get_text(id)` only — an element's `id` attribute
  to its first Text child. Matches the "existing text nodes only, no insertion/removal" v1 scope
  from the original decision, unchanged.
- **Event model**: `onclick="funcName"` on a bare `<button>` (SPEC's existing `FormControlKind::
  Submit`), intercepted in `BrowserView::handle_mouse_hit`/`handleEvent`'s `kbEnter` branch —
  `onclick` present → `run_onclick()` (relayout in place, no navigation); absent → existing
  `submit_form()` behavior, unchanged. No new HTML parsing needed: `dom::Node` attributes were
  already fully generic, and `<script>`/`<meta>` were already ordinary (if `display:none`'d) nodes
  in the tree gumbo builds — `dom::collect_lua_scripts`/`dom::find_meta_content` are pure
  tree-walks, no `dom/parser.cpp` changes.
- **Bundled, additive, not required**: `<form>` was deliberately dropped from the calculator's
  markup, not just left optional — this project's UA stylesheet sets `form { display: block; }`
  (`adr-extension-server`'s round-two note explains why that broke the pre-scripting version), and
  a bare `<button>` doesn't need a `<form>` ancestor for `FormControlKind::Submit` detection to
  fire. A page can still mix scripted buttons with a real `<form>` elsewhere on the same page.
- **Window-size/color `<meta>` hints landed alongside** (`tvshow-window-size`/`tvshow-window-
  color`, `BrowserWindow::apply_page_window_hints()`), bundled into the same pass since the user
  asked for both together. One non-obvious bug on the way: a live, in-place `changeBounds()` call
  on an already-visible window leaves stale pixels where the window used to extend — shrinking
  doesn't repaint what's now exposed behind it. `TGroup::drawUnderRect(oldBounds, this)` looked
  like the precise tool for this and **segfaulted** (crashed the whole app, not just a cosmetic
  glitch) when called from `BrowserWindow::tick_if_loading()`'s call path — root cause not fully
  chased down (likely a contract this call site doesn't satisfy, mid `Application::idle()`'s own
  window-iteration), but not worth cargo-culting past: `TGroup::redraw()` (a full `drawSubViews()`
  pass) is the safe fallback — repaints more than strictly necessary, never crashes.
- **CSS, not a `tvshow-window-color` hint, is what actually colors page content**: the window-color
  meta only reaches `BrowserWindow::getPalette()` — the TWindow frame/chrome. `BrowserView`'s
  content area is `CharGrid` the render pipeline paints straight from CSS, entirely separate from
  TView's palette system; a served page wanting a native-looking fill needs `body { background:
  ...; }` like any other page, not a tvshow-specific hint. Confirmed live, not assumed: an earlier
  round of this same testing pass chased a real-looking "the CSS isn't applying" bug that turned
  out to be this dev environment's own persisted `default-style = "tvision"` (`~/.config/tvshow/
  config.toml`, set earlier in the session) forcing every page's author CSS off — `skip_css =
  (forced_style != Auto)` in `BrowserView::navigate()`, working exactly as designed. Re-verified
  against a clean config to confirm the CSS itself was correct all along.
- **Calculator rewritten as a running-total accumulator**, not the AST-walking expression
  evaluator `calculator.py`/`calc_window.cpp` use — deliberately, not a shortcut: an accumulator
  never needs anything `load`/`eval`-shaped, keeping it consistent with stripping those out of the
  sandbox rather than needing a carve-out. No parentheses key as a result (an accumulator has no
  operator-precedence grouping to apply one to) — a different, still-valid calculator design.
  Verified live end-to-end (not just unit-tested): `8`, `-`, `7`, `1`, `3`, `=` in sequence
  correctly landed on `-705` (`8 - 713`), confirming persistent state survives many separate
  clicks and the arithmetic is right — with the window's URL bar never changing across any of
  those clicks, the actual proof the per-click page-reload/"blinking" problem this initiative
  existed to fix is gone.

## Round three: keyboard input + real color parity

User feedback after round two: mouse click worked, direct key-typing didn't, and colors still
didn't look native even with `default-style = auto` set. Two more real bugs, found live:

- **Keypress swallowed by focus, not missing entirely**: `BrowserView::handleEvent`'s `default:`
  case routes any printable/backspace key to `handle_form_input()` whenever *any* form control is
  focused — including a `Submit`-kind `<button>`, for which `handle_form_input` (built for text/
  textarea editing) is a no-op. Typing `7` while the `C` button happened to be focused did nothing,
  which reads as "keyboard doesn't work" even though Tab+Enter did. Fixed by checking, ahead of
  that switch, whether the typed character (or Backspace → `"<-"`) matches the `value` of *any*
  `onclick`-bearing button on the page — not just the currently-focused one, mirroring how the
  native `CalculatorWindow` responds to a key regardless of which button has visual focus. Verified
  live: typing `7`, `*`, `8`, `=` with no Tab presses at all landed on `56`.
- **Inline elements don't paint their own background**: `<span id="display">` styled via CSS never
  showed its `background: blue` — traced (live, via `tvshow-capture` A/B tests, not by reading code
  alone) to `background`/`background-color` only being painted for boxes that exist as their own
  `layout::Box` entry (block-level elements, form-control leaf boxes); a plain inline `<span>`
  contributes glyph tokens to its parent's inline flow with no box of its own to paint into. Swapping
  the display to a `<div>` (block) fixed it immediately — same fix documented in SPEC §7.2's Color
  row now, since it's a real, general engine boundary, not a calculator-specific quirk. Once that
  was found, `button { background: green; }` (already working — buttons are form-control leaf
  boxes) plus `#display { background: blue; color: white; }` on the now-block display gives the
  calculator its green-buttons/blue-LCD-display look, matching the native window's palette instead
  of just its background tone.
- **What was never actually broken**: the very first "colors are off" report traced to this dev
  environment's own persisted `default-style = "tvision"` (round two's finding) — real, but not a
  code bug; the user fixed it locally by setting `default-style = auto`, at which point the *real*
  remaining bugs above (block-vs-inline background, keypress-swallowed-by-focus) were the ones
  still worth chasing. Both confirmed fixed live in the same session, same screenshot-driven
  discipline as everything else in this ADR.

## Consequences

- SPEC §1.2 non-goal text changes from "JavaScript execution" to "arbitrary/untrusted client-side
  execution" — same file, same commit as this ADR.
- New Open Questions entry `q-sandboxed-scripting`, resolved-as-**Implemented** (see "Round two"
  above for what shipped vs. the narrower v1 scope still deferred).
- `q-websocket-support` (`adr-websocket-support`) gets a note: its revisit trigger ("scripting
  layer enters scope") is now **met** — scripting exists — but WebSocket support itself is still
  unbuilt; that's a separate ask this ADR doesn't take on.
- `EventViewerWindow` stays a native `TWindow` (unchanged) — nothing here required touching it;
  a script-driven rewrite is a real future option now, not done in this pass.
- New vendored dependency: `lua/lua` v5.4.7 (MIT), per `cmake/Lua.cmake` — see "Round two" for the
  vendoring details (this satisfies, not skips, `CLAUDE.md`'s "adding a new third-party dep
  requires an ADR" rule: this is that ADR, updated in place once the dependency actually landed).

## Alternatives Considered

*(For the underlying "how does a server-backed extension get live updates" question — scripting
was chosen over these two.)*

- **Meta-refresh-style polling** (extension page periodically re-fetches itself, or a fragment of
  itself): cheapest option, no SPEC change, no new dependency — rejected as the *only* answer
  because it caps at "eventually consistent, on a timer," not "instant," and doesn't help
  `EventViewerWindow`'s case (nothing to poll — the data is generated by local interaction, not an
  external resource).
- **Server push without a language** (e.g. long-poll or SSE-shaped mechanism, DOM patches
  expressed as a fixed data format instead of code): considered — doesn't need a new interpreter
  dependency or non-goal reversal. Rejected as less general than scripting: it can deliver "the
  page changed," but can't express "when the user does X, do Y" client-side logic (validation,
  computed fields, anything Calculator's HTML version currently needs a full round-trip for)
  without still growing into a bespoke mini-language anyway — at which point it's scripting with
  extra steps, just not admitted as such.
- **Do nothing / leave Event Viewer as the only "live" case, forever native**: rejected — it's a
  real gap in what `adr-extension-server` extensions can do that a future extension author will
  hit again, worth having a documented direction for rather than re-litigating from scratch next
  time it comes up.
